# Pairing and connection (phase 2.7)

How a tablet and Home Assistant find each other, authorise each other and decide which address to use.

## Goals
- Nothing is typed by hand in the normal case: the tablet is **discovered** (mDNS) and **confirmed**.
- The **tablet** generates the secrets for the handshake; Home Assistant must prove it was authorised (code) or be allowed
  by the person at the tablet (confirm). Home Assistant then hands the tablet its connection token over an encrypted channel.
- Without discovery (other VLAN, mDNS blocked) Home Assistant takes an IP + port + the code the tablet shows and pairs the same way.
- The persistent tablet -> Home Assistant WebSocket (see [PROTOCOL.md](PROTOCOL.md)) is unchanged; pairing only decides its
  token and address(es).

## Pairing mode (tablet)
Started by the user (System -> Pair with Home Assistant, or the setup wizard). For at most 10 minutes, or until a pairing
succeeds, the tablet

- listens on TCP **8750** (any free port if busy) and speaks the handshake below, and
- advertises `_ha-sidecar._tcp` over mDNS (Android `NsdManager`) with TXT records `id` (stable device id), `name`, `model`, `v=1`.

It shows a **code** (`XXXX-XXXX`, 8 characters from an alphabet without look-alikes) and its address(es). Outside pairing mode
nothing listens and nothing is advertised. Five wrong codes switch pairing mode off.

## Handshake (HTTP + JSON, `/pair/v1/...`)
Both sides generate an ephemeral **P-256** key pair and a 16 byte nonce.

| Step | Request | Answer |
|---|---|---|
| `GET info` | | `{id, name, model, pairing}` |
| `POST hello` | `{v, mode: "token"\|"confirm", ha_name, ha_nonce, ha_pub}` (public key as DER SubjectPublicKeyInfo, base64) | `{session, tablet_pub, tablet_nonce, id, name, model}` |
| `POST finish` | `{session, iv, ct, proof?}` | `{ok, id}` or `{error}` |

Keys: `shared = ECDH(own private, peer public)`, then HKDF-SHA256 (salt = `ha_nonce || tablet_nonce`, info =
`ha-sidecar-pair-v1`, 68 bytes) -> `enc` (32) | `mac` (32) | 4 bytes for the **comparison number** (`value mod 1_000_000`, six digits).

Authorisation in `finish`:
- **token mode**: `proof = HMAC-SHA256(mac, "ha-proof\0" + code)`. Constant-time compare on the tablet; no further interaction.
  The proof is bound to this handshake through `mac`, so it cannot be replayed or used to guess offline.
- **confirm mode** (what discovery uses): at `hello` the tablet shows "*Home Assistant* wants to pair" and the six-digit
  number; Home Assistant shows the same number. If a man in the middle sat between them the numbers would differ. The tablet
  user presses Allow (the `finish` call waits up to 90 s for that).

Credentials: `ct = AES-256-GCM(enc, iv, JSON{token, internal_url, external_url, ha_name}, aad = "ha-sidecar-pair-v1" + session)`.
`token` is generated by Home Assistant and is what the tablet later sends in its WebSocket `hello`. On success the tablet
saves token and addresses, adds its current Wi-Fi to the home networks (if it can read the name), leaves pairing mode and
connects.

Home Assistant side: manifest `zeroconf: ["_ha-sidecar._tcp.local."]`; the config flow has a *zeroconf* step (found tablet ->
name + entity prefix -> verify number -> done) and a *user* step (address, port, optional code). Cryptography uses the
`cryptography` package that ships with Home Assistant; the Kotlin and Python implementations are checked against shared test vectors.

## Which address, and when to be connected
Like the companion app the tablet knows an **internal** and an **external** address and decides per network:

| Where the tablet is | Address |
|---|---|
| Wi-Fi from the *home networks* list | internal |
| Ethernet (default: counts as home, switchable) | internal |
| VPN connected, with *VPN counts as home* on | internal (Home Assistant is reachable through the VPN) |
| anything else, and an external address is set | external |
| anything else, no external address | internal |
| nothing configured (no home Wi-Fi, no VPN flag) | internal: behaves as before |

The **persistent connection** setting: *Always* (default) stays connected on every network; *Home network only* keeps the
connection only while on a home network (otherwise the tablet idles instead of dialling out; kiosk, alarms and
timers keep working locally). The route is re-evaluated whenever the network changes (`ConnectivityManager` callbacks, debounced).

Reading the Wi-Fi name needs Android's location permission (an OS rule, the same one the companion app asks for); without it
Wi-Fi is "unknown" and the home networks list cannot be matched, VPN and Ethernet still work.

## Threat model (short)
- A device on the LAN can only pair while the user has pairing mode on, and needs either the on-screen code or the user's Allow.
- The code is single-use per pairing mode; five failures close it.
- Transport is plain HTTP on the LAN, but nothing sensitive is sent in the clear: the token is AES-GCM encrypted under keys
  only the two endpoints derive; the confirm number defeats an active man in the middle.
- Anyone who can read the tablet's app storage can read the token (same as before; Android app sandbox).

## Not done
- QR code on the tablet containing address + code (needs a QR renderer/scanner).
- Re-pair / reconfigure from the Home Assistant side (reconfigure flow).
- Pinning the peer's long-term identity after pairing (the ephemeral keys only protect the pairing itself).
